# Corpus annotation guide (STT POC)

This guide turns spontaneous recordings into a corpus the harness can
evaluate. The template for a descriptor is in
[`sample.template.json`](./sample.template.json).

> **Rule number one.** Do not transcribe the audio with an STT system to
> produce the reference. That is circular: you would be grading providers
> against the output of another provider. Every reference (`transcript_literal`
> and `order_expected`) is annotated by hand, by a human ear. If you break this
> rule, the POC stops measuring anything useful.

## Where the files go

- One JSON descriptor per sample in `voice-eval/samples/`, for example
  `voice-eval/samples/sample_001.json`.
- The **clean** source audio in `voice-eval/audio/`, for example
  `voice-eval/audio/sample_001.wav`. The descriptor's `audio` path is resolved
  *relative to the descriptor*, which is why the template uses `../audio/...`.
- You need **at least 20 valid descriptors**. With fewer, `load-samples.js`
  rejects the whole set before any API spend.
- Do not put templates or drafts inside `voice-eval/samples/`: every `.json` in
  that folder is treated as a real sample. That is why the template lives in
  `voice-eval/`.

Always annotate while listening to the **clean source** audio, not the degraded
conditions. Conditions B (WhatsApp) and C (telephony) are generated by the
pipeline from the source; the reference is annotated once, against the source.

## The contract fields

| Field | Type | Rule |
| --- | --- | --- |
| `id` | string | Non-empty and **unique** across the corpus. |
| `audio` | string | Path relative to the descriptor; the file must exist. |
| `speaker` | string | Anonymous, **consistent** id per person (`spk_01`, `spk_02`, ...). |
| `noise` | string | Environment label (`kitchen`, `street`, `quiet`, ...). |
| `transcript_literal` | string | The exact words spoken. |
| `order_expected.items` | array | Non-empty. One object per ordered item. |
| `items[].item` | string | **Canonical** product name (see aliases). |
| `items[].quantity` | number or string | Positive. Prefer a number (`3`, not `"tres"`). |
| `items[].modifiers` | array of strings | May be empty `[]`. Each modifier non-empty. |

`validate:corpus` checks **structure**, not quality. Passing validation does not
mean the order is annotated correctly; that is your responsibility.

## `transcript_literal` vs `order_expected` are different things

Do not derive one from the other mechanically.

- **`transcript_literal`** is the words as spoken, filler and all:
  `"eh... me das tres tacos al pastor y una horchata grande porfa"`. It is used
  to debug why a provider failed.
- **`order_expected`** is the canonical, structured order: what the kitchen
  should produce. The example above yields two items: `taco al pastor x3` and
  `agua de horchata x1 (grande)`.

## How to annotate `order_expected` (the part that matters most)

1. **Annotate the customer's intent, not what you hear in the noisy audio.**
   The ground truth is what the person ordered. If you have the real ticket or
   order for that recording, cross-check it and use it to confirm items and
   quantities. Annotating by ear from the degraded signal contaminates the
   reference with the same errors you want to measure.

2. **Every ordered item must appear.** The POC guardrail measures missing
   items (deletions). If you forget an item the person did order while
   annotating, you inject a *phantom deletion* into the reference and the
   guardrail ends up measuring your oversight, not the provider's. Count the
   items against the real order before closing each sample.

3. **Canonicalize with `voice-eval/aliases.json`; do not invent equivalences.**
   The name in `item` must be the canonical form. Aliases map spoken variants
   to one canonical name, for example:
   - `"hot dog jumbo"` <- `hot dog`, `hotdog`, `perro caliente`
   - `"hamburguesa de dos carnes"` <- `hamburguesa doble carne`, `doble carne`
   - `"bbq"` <- `barbecue`

   If a product or variant appears that is not in `aliases.json`, **do not
   resolve it in the annotation**: add it to the aliases file first and then
   use it. Equivalences live in exactly one place.

4. **Quantity as a number whenever possible.** Spoken `"tres"` is annotated as
   `3` in `quantity`. The scorer treats `"tres"` and `3` as equivalent, but the
   number is cleaner and less ambiguous.

5. **Modifiers only if they change what the kitchen does.** `grande`, `sin
   cebolla`, `para llevar`. If there are none, leave `[]`.

## Make the corpus worth it (20 is the floor, not the goal)

A corpus of 20 trivial single-item orders proves nothing. For the finding to
mean something, spread out the variety:

- **Several speakers.** Not one voice repeated; use distinct `speaker` ids.
- **Several noise environments** in the `noise` label.
- **Cases that exercise the scorer:** spoken quantities (`"dos"`, `"media
  docena"`), aliases (`hot dog` / `hotdog`), modifiers, and **several
  multi-item orders** where losing an item would be costly. Those are the ones
  that put the deletion guardrail to the test.

## Quality control

- **Have a second person verify part of the corpus.** The same principle as
  the rest of the project (whoever builds something is not the one who verifies
  it) applies to annotation: the annotator has blind spots.
- Re-listen to at least the multi-item samples: that is where a phantom
  deletion slips in most easily.

## Closing the blocker

Once you have the 20 or more descriptors and their audio:

```bash
cp voice-eval/config.example.json voice-eval/config.json   # if it does not exist yet
npm run validate:corpus -w voice-eval
```

Expected output: `Validated N samples and M alias entries.` with `N >= 20`.
That closes the human blocker.

## What comes next (and what does NOT)

Having the corpus does **not** unblock provider calls. The next code milestone
is the **scorer** and its verification (Gate 2): prove, on hand-written fake
transcripts, that a deletion and a substitution are reported separately,
**before** spending on any API. A broken scorer cannot be seen in the results
table, which is why it is verified first. Ideally someone other than the
implementer verifies it.
